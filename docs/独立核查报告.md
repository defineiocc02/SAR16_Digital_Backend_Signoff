## 三条必须整改的发现 → 现状：**两条作废，一条已由本方还原**

**1. [已作废] 交付网表没有定义复位。**  *（第 26–28 轮反向追踪与无 force 重测证明：`rst_n` → INVX8 → HFSNET_124 → 反相器 → HFSNET_119 → 两个子模块 rst_n，复位工作正常。本条系本方测量错误。）*
原判依据是"tie 根值未写出 ⇒ 复位锁死"；实际那条链是**反相器链**，根就是 `rst_n` 本身。

**2. [已作废] 即使复位正确，主状态机不前进。**  *（第 29 轮与第 31 轮在正常复位下重测：`state` 000→010→011→100→101、`busy` 0→1、`residue` 已发布 —— 本条系本方测量假象。）*

**3. [仍成立，但已可闭环] `gen/gen_srm_lut.py` 不在交付件里。**
RTL 三处点名它（含一条 `$error`"用它重新生成"），六路搜索整个 home 均无此文件。
⇒ 那张硬编码表**无法重生成、无法审计**，而它是 `residue_o` 的全部数值来源。
**本方已按 RTL 注释还原生成器（`tools/gen_srm_lut.py`），在 H2 假设下对交付表体逐项复现 12/12**，
偏离原因因此从"无法裁定"变为"已定位"；但**交付件本身仍缺这个脚本**，这项整改依然有效。

顶层放置 **115 种 master**（6 种 `$$via` + 109 种库单元）/ **34 356 个 SREF**

> **两条早先写进本报告的"异常"已撤回，成因都是本方解析器错：**

## 关于本次核查的诚实说明

核查与修复过程中我**撤回或更正过自己的 12 处结论**，其中 **4 条曾被当作"交付方缺陷"写进本报告**：

| 被撤回的"发现" | 真实原因 |
|---|---|
| 交付网表没有定义复位 | 把一条**反相器链**当成了未写值的 tie 根 |
| 主状态机不前进 | 在**错误的复位假设**下取数 |
| GDS 顶层 cell 没有任何几何 | 我的 **GDS 记录码表写错**（0x08 才是 BOUNDARY） |
| GDS 放置 3 735 vs 网表 3 626 / master 224 种 | 把**全文件** SNAME 计数当成顶层放置；后又有一处 `len(set(k[1] …))` 把**字符串第 2 个字符**当 master 名 |
| 顶层 `total_count` / `ones_count` 读数为 0 | 我的测试台生成器**丢掉了端口位宽**，把 5 位总线声明成 1 位，只读到了 LSB |

另有：hold 39 不可复现、residue 容差用错导致"吻合"抢跑、`FM-399` 口径、`sed` 破换行等。
**教训固定为三条规矩**：① 每条结论必须有对照；② **检查必须先证明自己跑过**（本轮又栽在两次
"零结果"上：`$time` 单位判断错、`integer max=-1` 的有符号比较使最大值统计成了死代码）；
③ 不引用自己没有实测过的计数。逐条记在 `_过程记录/`。
