**三条第一手线索（README 里没写，是我从报告原文读出来的）**：

1. **差异高度集中在电源网**：`INCORRECT NETS` 第一条就是
   `Net VDD — layout 15246 Connections / source 13747 Connections`（**+1499**）。
   这比任何信号网都大一个量级。
2. **归并后器件差只剩 +11/+21**，而初始差是 +406/+437 —— 说明**大部分初始差会被 Calibre 的
   器件归并吃掉**，真正需要解释的是"归并不掉的那部分"。
3. **有三类器件只在版图侧出现**：`_bitcorev (4 pins) 1 vs 0`、`_pup3b (6 pins) 1 vs 0`、
   `_smn2b (5 pins) 1 vs 0`；另有 `_invv −26`、`_nand2v −7`、`_sdw2v +10`、`_mx2v −2`。
   配合 `INCORRECT NETS` 里 "layout 的实例名是 `VSS`、source 的实例名是 `WEIGHT_RD_DATA[0]`"
   这类**同功能不同名**的配对 —— 与被打断方"tie / injected instance"的假设**方向一致**，
   但收窄到了"电源网 + tie 类实例"。

**一个口径要点**：源网表是 `v2lvs -v pnr/out/sar_digi_paper_core_pnr.v` 转出来的**后布线网表**
（`run_lvs_paper_core.sh:113`），所以 **CTS 插入的缓冲器不是差异源**，两边都该有。

## 4. 复核期间我自己的两次错（记下来，免得误导后面）

1. **GDSII 记录号写错一位**：把 `0x19=STRING` 当成 `MAG`，第一版数出"顶层 234 个 TEXT 元素、
   但 0 个标签" —— **与被打断方记忆里警告过的"TEXT(0x0C) 与 STRING(0x19) 写混"是同一个坑**。
2. **LEF 的裸 `END` 被当成 macro 结束**：`PORT … END` / `OBS … END` 用的是裸 `END`，
   导致第一版数出"113 MACRO / 112 PIN"（≈每 macro 一个 pin）。
   **两次都是"解析器自己错、结果却像审计结论"**。最终数字全部改用可人工复核的
   `Select-String ^MACRO` / `^\s*PIN` 双口径确认。
