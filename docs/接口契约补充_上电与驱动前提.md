## 3. [已作废] 原「上电前提」原文（留痕）

**`rst_n` 端口在交付网表里未被使用。** 两个最大子模块的复位来自一条**网表没有写出值**的
tie 常量链：`HFSNET_120…124 → HFSINV → HFSNET_119 → rst_n`。

**实测后果**（自写测试台）：

| 现象 | 值 |
|---|---|
| 顶层 `rst_n` 从 0 抬到 1 | 两个子模块的 `rst_n` **不跟着变** |
| 网表自己解析出的 tie 根 | **1** ⇒ `rst_n = 0` ⇒ **复位常驻** |
| 结果 | `busy` 恒 0、`total_count` 恒 0 —— **主功能不工作** |

**因此，按原样使用本网表时，集成方/验证方必须：**
1. 知道存在这条 tie 根（`HFSNET_120…124`）；
2. 把它当**复位序列**驱动：**先 1（断言复位）→ 再 0（释放）**；只置 0 会让触发器停在 X；
3. 不要指望用顶层 `rst_n` 复位这两个块。

**★ 与 `gen/gen_srm_lut.py`**：该脚本已在修复 06 中还原到 `gen/`，
`residue_o` 的表可用 `python3 gen/gen_srm_lut.py --n 22 --sigma-q8 128 --frac-out 8` 重生成，
与交付 RTL 表体 **12/12 一致**。

## 4. 门级仿真前提（第 34 轮实测更新）

- 现有 `pwr_gls` 那次 GLS **编译的是交付网表**，但**零延迟、只为产 SAIF、无 PASS/FAIL**；
- 交付网表**本身可仿真、可判定**：自写 TB（无 force）下顶层端口给出
  `srm_total_count=22 / srm_ones_count=7 / srm_residue_o=966`，与 RTL 同激励结果**逐位相同**；
- **读总线端口必须带位宽**（`wire [4:0] srm_ones_count;`）。声明成 1 位会被静默截断为 LSB——
  这正是早先"顶层计数读数为 0"的**唯一**原因（第 34 轮，见 `_过程记录/修复15`）；
- `rst_n` 与普通同步复位一样用即可，**不需要任何特殊复位序列**（§3 已作废）。

## 4b. 一条实测的时序契约：判决接受窗口

`srm_start` 拉高后，估计器**晚一个时钟槽**才武装判决域；随后接受**接下来 22 个**
`srm_decision_valid` 的判决。实测（同一激励、同一网表，只把判决流相位挪一个槽）：

| 相位 | 顶层结果 |
|---|---|
| 判决流从第 0 槽起 | `total=22 / ones=8 / residue=981` |
| 判决流从第 1 槽起 | `total=22 / ones=7 / residue=966` |

RTL（零延迟）在同一激励下给第 2 行。⇒ **两侧逻辑一致，差的是一个槽的相位，
来自网表真实时钟树（时钟门 + GLS 缓冲）相对零延迟 RTL 的延迟**。
集成方若对 `ones_count` 做逐位比对，必须按**实际武装时刻**对齐判决流。
