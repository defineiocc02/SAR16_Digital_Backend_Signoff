## 1. 悬案是什么

`修复13` 第 4 节留了一条：**状态机完整走完、`residue` 已发布、`shortfall=0`，
但顶层 `srm_total_count` / `srm_ones_count` 读出来是 0**，与"设计认为收满了 22 个判决"自相矛盾。
当时列了两个可能：① 顶层端口连的不是那个寄存器；② 读的时机/口径不对。**本轮把两者都排掉。**

## 2. 排除①：连接是好的（静态 + 动态双重对照）

静态（`tools/net_trace.py`，**模块作用域**内追踪）：

```
n103 <- NAND2XL U80 .Y()  inputs: A=n7 B=cap_ones[4]
n7   <- INVX2  U72        A=n41 ;  n41 <- NAND2XL U50 (state[2], n53) ; n53 <- NOR2XL U49 (state[0], state[1])
```

`ones_count_reg[0..4]` / `total_count_reg[0..4]` 确实存在（网表 L317–336，与 `residue_q_small_reg`
共用时钟门 `net1643`），QN 直接驱动 `ones_count[k]`；顶层再由 `HFSBUF_2_301..320` 缓冲到端口。

动态（`probes/fix15_count.sh`，逐周期打印，**并打印"监视器跑了多少个周期"以证明检查确实跑过**）：

```
C t=856000 st=101 | SUB one=8 tot=22 q=981 | TOP tot=22 one=8 res=-43
     | NET 109=0 110=1 113=0 | NET 114=1 115=0 118=0 | NET 121=1 130=1
```

顶层连接网 `aps_rename_*` 的值与子模块内部 `8 / 22 / 981` **逐位吻合**，
且这些值在 S_HOLD 里**稳定保持十几拍**（不是只出现一拍）。⇒ **连接没问题。**

## 3. 真因：我的测试台把总线端口声明成了 1 位

测试台的 DUT 封装是脚本从网表端口表自动生成的，生成时用了

```python
nm = lambda p: p.split(']')[-1].strip() if ']' in p else p   # 只取名字，丢掉 [4:0]
L.append('  wire %s;' % nm(p))                                # -> wire srm_ones_count;  (1 位!)
```

输出端口是 5 位，接在 1 位网上 → **静默截断为 LSB**。于是：

| 端口 | 真值 | 读到 | 为什么 |
|---|---|---|---|
| `srm_total_count` | 22 = `10110` | **0** | LSB = 0 |
| `srm_ones_count` | 8 = `01000` | **0** | LSB = 0 |
| `srm_residue_o` | 981 = `1111010101` | **−1** | LSB = 1，且只有 1 位 ⇒ `$signed` = −1 |

**三个"异常值"全是 LSB——这就是指纹。** 单比特信号（`busy`/`done`/`residue_valid`）从来没出错，
因为它们本来就只有 1 位。**同一个生成器还被 `fix14`、`v2f_state`、`v2ind` 用过，
所以这解释了整个"网表读不出计数"的假象链。**

修正为 `L.append('  wire %s;' % p)`（保留位宽）后重跑：

```
MAX  top_total=22 top_ones=8 | SUB_total=22 SUB_ones=8 | dec_total=22 dec_ones=8 | cap_total=22 cap_ones=8
```

**顶层端口 = 子模块输出 = 计数域寄存器，三层一致。**

## 4. 顺手做掉的一处口径差：RTL 7 vs 网表 8

同激励下 RTL 给 `total=22 / ones=7`，网表给 `total=22 / ones=8`。**这不是丢/多一个判决**：

- 判决流是 `f(i) = (i mod 3 == 0)`，接受窗长 22；
- `#{i∈[0,21]} = 8`，`#{i∈[1,22]} = 7` —— 差一个槽正好差一个 1；
- 网表有真实时钟树（时钟门 + GLS 缓冲），`start` 到武装比零延迟 RTL 晚一个槽。

**判据（可证伪的预测）**：把送出的判决流相位挪一个 `dec_clk` 槽，网表应给出 **7**。
实测：

```
MAX  top_total=22 top_ones=7 | ... | dec_total=22 dec_ones=7 | cap_total=22 cap_ones=7
C t=966000 ... SUB one=7 tot=22 q=966 | TOP tot=22 one=7 res=-58
```

**RTL（相位 0，`probes/fix16_rtl_same_stim.sh`）给 `total=22 / ones=7 / residue=966`** ——
与上式**逐位相同**。即 **RTL@相位0 ≡ 网表@相位1**；`total=22` 在三例中全部一致，
差的只是一个槽的接受窗相位，**不是丢/多判决**。
