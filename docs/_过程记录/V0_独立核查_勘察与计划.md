## 2. "布线为什么这么散"——**是一个参数**

`scripts/fc_pnr_paper_core.tcl`：

```tcl
set UTIL 0.55
...
initialize_floorplan -core_utilization $UTIL
```

`pnr/reports/fc_util.rpt` / `fc_area.rpt` 实测：

| 项 | 值 |
|---|---|
| 单元总面积 | **102 300.11 µm²** |
| 核心/块面积 | **184 066.34 µm²** |
| **利用率** | **0.5558** |
| 单元数 / 组合 / 时序 | 3626 / 2575 / 1051 |
| buf+inv | 521 |

**⇒ 单元只占了 55.6 % 的核心面积，约 44 % 是空行。这不是布线失败，是 `UTIL` 这个数。**

**代价必须一起说**：`fc_congestion.rpt` 显示当前已有溢出——

```
Both Dirs  overflow total 511   max 4   GRCs with overflow 364 (2.52%)   max 7
V routing  overflow total 427           GRCs with overflow 297 (4.11%)
```

**⇒ 55 % 下布线器已经有点挤。** 紧凑化空间**存在但需要实验确定**，不能直接宣称能压到 70 %。
下一轮做 UTIL 扫描（0.55 基线 → 0.65 → 0.70）的单变量实验，每个点看
利用率、congestion 溢出、slow slack、DRC/LVS 是否守恒。

## 3. 独立核查计划（按顺序，每条都有对照）

| 编号 | 核查项 | 方法 | 判据 |
|---|---|---|---|
| **V1** | RTL ↔ **交付 P&R 网表** 等价性 | Formality，参考 RTL、实现 `pnr/out/…_pnr.v`，带 SVF | 无 failing 点；unmatched 点逐条解释 |
| **V2** | **独立参考模型**功能核查 | 自写 Python 金模型 + 自写 testbench，用 VCS 驱动，比对行为 | 逐拍/逐笔比对一致；不一致必须能解释 |
| **V3** | 交付网表**可仿真性** | 检查 `HFSNET_*` 无驱动在仿真中的后果 | 若 X 传播 ⇒ 记录为交付件缺陷的实测后果 |
| **V4** | 布线密度与紧凑化 | UTIL 扫描单变量实验 | 给出密度—congestion—时序的三方权衡，而不是一句"能压" |
| **V5** | 时序 / DRC / LVS 结论复核 | 从原始报告重新解析，不用二手数字 | 与交付报告逐项对齐，不一致处列出 |

**先做 V1 与 V3**：它们决定"功能实现了吗"这个问题能不能给出肯定回答——
如果交付的布线后网表与 RTL 不等价，那么功能就**没有**被独立确认过。

## 4. 本轮已确立的结论

1. **功能有过形式验证，但只到综合网表这一层，且早于全部 v5.x 修改**；交付的布线后网表从未被等价性核查。
2. **布线散的根因是 `set UTIL 0.55` 一个参数**，不是布线器没做好；紧凑化有空间，但受 congestion 制约，需实验定量。
