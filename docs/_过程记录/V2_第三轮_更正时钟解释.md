## 1. 更正：**没有"片上振荡器"这回事**

上一轮我写"`u_srm_residue` 的功能时钟是片上生成的内部时钟 `ctosc_gls_0`，振荡器没跑"。
加模块作用域后，事实是：

```
模块 srm_residue_estimator_DECISION_COUNT22_…  （块内）
  L414  BUFX1 ctosc_gls_inst_1717 ( .A ( dec_clk ) , .Y ( ctosc_gls_0 ) ) ;   ← 块内局部网

模块 sar_digi_paper_core                        （顶层）
  L6425 CLKBUFX8 ctosc_gls_inst_1718 ( .A ( clk ) , .Y ( ctosc_gls_0 ) ) ;    ← 顶层唯一驱动
  L6160 .clk ( ctosc_gls_0 ) , .rst_n ( HFSNET_119 ) ,      ← u_calib_ctrl.clk
  L6212 .decision_bit ( … ) , .clk ( ctosc_gls_0 ) ,        ← u_srm_residue.clk
  L6249/6255/6263  DFFSX1 \raw_code_o_reg[*] ( … .CK ( ctosc_gls_0 ) … )
```

**两条结论**：

1. **顶层 `ctosc_gls_0` 只有一个驱动：`CLKBUFX8( clk )`。**
   ⇒ **不存在双驱动网**（我原先看到"两个实例都驱动 `ctosc_gls_0`"是**跨模块同名网**，
   我先查了作用域才没有把它写成缺陷——这一步是对的）。
2. **`u_calib_ctrl.clk` 与 `u_srm_residue.clk` 都由顶层 `clk` 经缓冲驱动。**
   ⇒ **我上一轮说"块一次都没被时钟沿打到"是错的**：块**是被 `clk` 打到的**，
   我的测试台确实驱动了 `clk`。`ctosc` 这个名字是 DC 生成时钟门封装带出来的遗留命名，
   与"振荡器"无关。

**⇒ 所以 `busy=0 / total=0` 的原因不在时钟，而在我的激励/协议。**
上一轮那份文档的结论（"顶层端口不足以驱动这个设计"）**作废**，此处更正。

## 2. 从 RTL 读到的握手事实（下一轮据此改激励）

```
input  logic  start,        // one-clock pulse to begin acquisition
output logic  busy,
output logic  done,         // one-clock completion strobe
output logic [4:0] total_count,   // decisions observed (== DECISION_COUNT unless shortfall)
output logic       count_shortfall,
L309:  else if (start && !busy) go_tgl <= ~go_tgl;     // start 是 clk 域，经 toggle 同步到 dec_clk 域
parameter DECISION_COUNT = 22, STALL_CYCLES = 64
```

要点：
- **`start` 是单时钟脉冲**（我在 TB 里给了 20 ns = 2 个 `clk` 周期，形式上够）；
- 起振走的是 **`clk` 域 → `dec_clk` 域的 toggle 握手**（`go_tgl`），
  因此**两个时钟都必须跑**，且 `dec_clk` 要有足够边沿让握手同步过去；
- `total_count` 正常应等于 `DECISION_COUNT`（22），除非 `count_shortfall`；
- 块内还有 `SNPS_CLOCK_GATE_*` 门控单元，其 `ctosc_gls_0` 来自**块内** `BUFX1(dec_clk)`。

**下一轮要查的具体机制**：`busy` 是否在 start 后应当立刻变高？若是，
则我的 start 脉冲没有生效（时序/域问题）；若 `busy` 只在 `dec_clk` 域内抬升，
则我的判据取错了域。**先读 `busy` 的驱动条件，再改激励**，而不是盲试。
