# 修复 07b：SREF 计数**再次更正**——我上一轮的两个数都不成立

**日期**：2026-09-19 ｜ **状态**：❌ 未查清；**但把"哪些数是错的"划清了**

---

## 1. 发生了什么事

上一轮我用"**全文件**的 SNAME 计数"当作"顶层放置数"，得出：

```
顶层 SREF 34 465 ; 其中 $$via 30 730 ; 余下 3 735 ; distinct masters 224
```

本轮把 SNAME 的计数**限制在顶层 cell 内**（`if cur == TOP`）后：

```
=== SREFs in the TOP cell ===
  distinct masters referenced : 11
  total SREF count            : 34356
```

**⇒ 一收窄到顶层，数字就变了：11 种 master、34 356 个 SREF。**

## 2. 因此这几条**全部作废**

| 我说过 | 为什么错 |
|---|---|
| 「顶层 real cell placements = **3735**，比网表 3626 多 109」 | 那是**全文件** SREF 减过孔，**不是顶层放置** |
| 「顶层引用 **224** 种 master」 | 同样是**全文件**口径 |
| 「109 恰好等于库单元种类数，像是包装层与内层各被引用一次」 | 这是**基于错数的猜测**，一并作废 |

**⇒ 核查报告里"GDS 两处异常"中的第二处（3735 vs 3626）不是版图异常，是我的计数口径错误。**
（第一处"顶层无几何"已在修复 07 更正：记录码表写错。）
**⇒ 两处"异常"都不是被核查件的问题。**

## 3. 但新的数字也**还不能用**

顶层只有 **11 种** master 引用 —— 这与"3626 个单元、109 种"**对不上**，
说明**这个 GDS 的放置层次与我假设的不同**（顶层可能先引用少数几个中间 struct，
单元在那一层才被放置）。

**这条我不知道答案，本轮不猜。**
要查清只需一步：把顶层那 11 个 master 的**名字**打出来，
再逐个看它们各自引用了什么。
